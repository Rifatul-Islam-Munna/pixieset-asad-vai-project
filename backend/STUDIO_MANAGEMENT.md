# Gallerista Studio Manager

Studio Manager is available at /dashboard/studio-management/home and from the product switcher. The layouts are based on the 17 screenshot references in design/ and use Gallerista's purple (#6337d8), white, and neutral-gray theme.

All studio records are tenant-scoped in MongoDB using the authenticated backend user ID. The existing Booking module powers session types, sessions, calendar events, and public booking. No demo records are seeded.

## Modules

- Home: real record counts, currency-separated paid revenue, recent projects and upcoming bookings.
- Projects: create/edit/delete, drag-and-drop stages, list, archive/restore, custom stages, project type filters, paid amounts by currency, and linked clients.
- Projects list visibility fix: Board View and List View are display modes, not project statuses. Neither view applies a false status filter; Inquiry and other existing active projects now show in their correct board columns or list rows, including custom stages.
- Project Board now uses compact 175px-wide columns and dense cards. Add Stage opens a titled modal with preset/custom hex colour controls and a live preview. Project stage names and colours persist in Settings (projectStages/projectStageLabels/projectStageColors), and the Project Detail status badge uses the saved labels and colours.
- Project List and Archived use full available content width, an anchored menu rendered above table overflow, and server-side search/type/archived/newest-or-oldest pagination with 10/20/50/100 rows per page. Project title links and clicks elsewhere in the row both open the same Project Details route as Board cards; menus and stage controls do not trigger row navigation.
- Project creation: /dashboard/studio-management/projects/new is a minimal three-field form matching the reference layout (Client, Project Name, New Project Type). The Client input searches existing Contacts by name or email across the tenant's records, with an inline Create New Contact panel (first/last name, email, optional phone). Creating a contact selects it automatically. The selected Contact is mandatory, and its owner-scoped ID is linked on project creation. New projects start in the Inquiry stage and navigate directly to Project Details.
- Project Details: open from a project card/row at /dashboard/studio-management/projects/:id. Reference-style two-column view with back navigation, stage selector, More/Archive/Delete, Create New (invoice/contract/questionnaire/quote/session), currency-separated Paid/Upcoming/Past Due, linked document rows and actions, editable session list, outgoing project messages, directly linked Client Gallery collections, primary/additional clients, location/description, and staff-only notes.
- Brand-new empty projects show a reference-style Get Started screen instead of empty Payments/Documents/Sessions lists: document shortcuts (Invoice, Contract, Questionnaire, Quote), a Session shortcut, and a Client Gallery Collections link-picker. No Conversations shortcut appears in Get Started; project messaging remains available from the populated detail page. The right-side Project Details and private Notes remain present in both states. When linked project records are created, the page returns to the regular detailed dashboard.
- The Inquiry/project-stage badge is an interactive selector, including studio-configured custom project stages (plus Cancelled/current status). Selecting a stage saves via PATCH /studio/projects/:id and refreshes the displayed status.
- Project Details edits open in a full-height right-side sheet, not a generic modal: primary/additional Contacts, project name/type, optional date, location and description. Changing project dates, including clearing them, persists to the tenant-scoped project without replacing linked notes or galleries.
- Contacts: client/lead details with separate first and last names, required email, phone, full address, CSV export across all pages.
- Contact Forms: full-page designer, dynamic fields, live preview, design colors, publishing, secure client link; submissions create contacts and inbox messages.
- Inbox: unread/read/sent tracking for forms, questionnaires, and outbound SMTP emails, plus compose-email and reusable email templates.
- Invoices: full-page editor, design colors, business name and footer, live preview, server-calculated items, discounts and tax, SMTP sending, public invoice print, manual payment recording and transaction history.
- Payment Links: full-screen reusable designer for title, description, site subdomain, custom URL path, active/draft status, fixed/preset/flexible amounts, optional tips, uploaded cover image (JPG/PNG/WebP/AVIF, max 5 MB), confirmation message, and optional automatic project creation. Existing legacy payment links remain manual; newly configured links use hosted Stripe or PayPal checkout with the owner's existing Store credentials. The public form collects payer first/last name, email and optional message, and works at /studio/payment/:token or https://<owner-subdomain>.<ROOT_DOMAIN>/payment/<slug>.
- Payment connections: Studio Manager -> Settings shows the same owner-scoped Stripe and PayPal credentials stored in StoreSetting.paymentMethods and used by Store Gallery. Saving changes updates only the shared payment methods, not Store catalogs, currency, shipping, or store availability. Saved secrets are masked in responses. Studio Invoice payment pages can create a Stripe-hosted checkout or PayPal approval order using the owner's existing account. Verification retrieves the provider checkout/capture, compares owner, invoice, amount and currency, and atomically records the invoice as paid plus a transaction. Only sent invoices with supported currencies and positive balances can be paid online.
- New Studio financial records (invoices, booking session types and payment requests) default to EUR. Existing records and old currency-specific financial results retain their original denominations; no money is automatically converted.
- Transactions: All Payments, Paid and Refunded tabs; staff-recorded invoice payments and verified online invoice/payment-link transactions, payer, provider, base amount, tip and total. After verifying a payment-link charge, the backend reuses/creates its contact and creates one linked project, protected from duplication by a unique source-payment index. The linked project's Payments section and Board paid totals include that receipt without counting invoice transactions twice.
- Reports: server-aggregated all-time invoice and payment totals, separate currency balances, overdue balances, and monthly charts.
- Session Types: full/mini, pricing, location, duration, visibility, custom hours, advance booking rules, intake questions, manual-payment setting and confirmation messages.
- Sessions: create/edit/delete, status, filters, linked to existing booking engine.
- Calendar: month, week and day views, status filters, bookings and blocked events, and revocable read-only .ics calendar subscriptions.
- Booking Site: client-facing booking URL, hours, time zone, booking policies.
- Discounts: studio discount records and expiry (not automatically applied to checkout).
- Contracts: a dedicated full-screen rich-text editor using the reference layout (document title/status, toolbar, signer/party details, editable letter page, variable placeholders, design colour, preview, save draft, email send and copy link). Eight editable starter templates cover general photography, wedding, portrait/family, event, commercial/licensing, videography, camera-equipment rental and model release. Saved custom templates can be edited and reused. Contracts created from Project Details or assigned a project in the editor appear under that project. The default Preview displays the same resolved public document and signature controls as a client sees. The owner may draw or type a studio signature, explicitly consent and save it to a draft before sending; changing signed text requires removing that owner's signature. Client signers independently draw or type and consent to their own signature on the real public link. Client signatures are recorded with timestamps by the backend. Public and preview signatures are displayed as safe bounded numeric paths or escaped text, never SVG/HTML uploads. Missing variables render as dashes. Server-side validation permits a safe subset of TipTap document nodes and links, and locks sent contract text.
- Questionnaires: dedicated full-page reference-style builder with client/project sidebar, title and description card, stable unique question keys, green Add Question menu, multiple-choice single-select, multi-select checkboxes, optional Other answers, short answer, paragraph, date and dropdown inputs, required questions, design accent, preview and Save/Send. The public page renders the actual input types, validates them on the server and records client responses in the studio Inbox. Sent questionnaires are read-only and optional expiry prevents late submissions.
- Quotes: a client/project selection step and full-page item builder with standard fixed items, required client-selection groups, optional add-on groups, item descriptions, quantities, prices, percent discount/tax, notes, currency, auto-create invoice, design accent and live preview. Public quotes support interactive choices and recalculated totals. The server validates selected option IDs and calculates actual pricing before acceptance. The client confirms using a typed acknowledgement; if enabled, a linked draft invoice is created after acceptance (a unique quote-source key prevents duplicates). Sent quotes are read-only. Legacy flat-amount quotes remain readable.
- Templates: create a new contract/questionnaire/quote/invoice from a template with client/project assignment, or compose a new email from an email template.
- Settings: studio contact information and custom project stages.

## API

Authenticated: /studio/overview, /studio/:kind, /studio/:kind/:id, /studio/invoices/:id/send, /studio/invoices/:id/record-payment, /studio/documents/:id/send, /studio/templates/:id/use.
Public token endpoints: /public/studio/forms/:token, /public/studio/invoices/:token, /public/studio/payment-links/:token, /public/studio/contracts/:token, /public/studio/questionnaires/:token, /public/studio/quotes/:token, plus relevant submit/accept routes. Reusable payment-link APIs: authenticated GET /studio/payment-links/sites and POST /studio/payment-links/cover-image; public GET /public/studio/payment-links/site/:site/:slug, GET /public/studio/payment-links/:token/details, and rate-limited POST /public/studio/payment-links/:token/checkout and /verify. Frontend /api/studio/payment-link-cover proxies authenticated uploads to object storage.
Public mutation routes have request throttling. Share links use random 256-bit tokens.

Additional routes: GET /studio/projects/payments, GET /studio/projects/:id/overview, POST /studio/projects/:id/notes, DELETE /studio/projects/:id/notes/:noteId, POST /studio/projects/:id/collections, DELETE /studio/projects/:id/collections/:collectionId, GET /studio/reports/summary, POST /studio/messages/send; GET /studio/calendar-sync, POST /studio/calendar-sync/rotate, POST /studio/calendar-sync/enable, DELETE /studio/calendar-sync; GET /public/studio/calendar/:token; GET /api/studio/calendar/:token.ics on the frontend. Disabling a calendar subscription persists, and its prior secret URL is revoked until the studio explicitly enables sync with a new token.

Project Details API queries are scoped to the authenticated user ID and project ID, and private notes and gallery membership use targeted MongoDB writes. Projects can be linked only to collections owned by the same studio. Creating manual sessions from a project validates linked project/contact ownership before saving, and inserts the event into the shared Studio Booking calendar. Existing project notes/gallery links are not overwritten by project editing.

Contact lookup accepts a case-insensitive, escaped literal search term using GET /studio/contacts?search=..., returning a paginated tenant-owned list. Server-side project creation also requires a valid owned Contact ID (not just a typed name). An email already found in Contacts is reused by the quick-create UI rather than adding a duplicate.

Public bookings now automatically upsert a Studio Manager contact and create a linked project. Pending bookings create inquiry projects; confirmed bookings create booked projects and client contacts. Later booking confirmation, completion, cancellation and event deletion update linked project stages.

## Deployment

Deploy frontend and backend together. Ensure the existing MongoDB, object storage and SMTP environment configuration is valid. Set FRONTEND_URL in the backend for emailed links and use matching ROOT_DOMAIN or NEXT_PUBLIC_ROOT_DOMAIN on the frontend and backend for owner-subdomain /payment/:slug links. The Next.js proxy rewrites these URLs to /studio/payment-site/:site/:slug; the backend validates site ownership. New unique partial MongoDB indexes enforce payment-link slug uniqueness per owner/subdomain and one project per confirmed payment. Verify indexes on deployment.

Test with a real staging account: create a contact, project, invoice, and form; submit the form through its public link; send an invoice and document using SMTP; record a manual payment; create a full and mini session; check availability, booking rules, custom intake questions and calendar events.

## Limitations

1. Online Stripe Checkout and PayPal approval are implemented for **sent Studio invoices and newly configured reusable Payment Links** when the owner has enabled matching Store credentials. Older manual Payment Links remain manual until configured with a valid URL slug; Session Types still use manual payment reporting. No credentials or payments were verified against a live gateway in this development pass.
2. Studio discount records are not automatically applied to public booking checkout.
3. Contract studio and client signatures may be drawn or typed, and quote acceptance remains a typed acknowledgement. These workflows are basic recorded consent, not certified e-signatures or identity verification.
4. Invoice charts and report totals are computed by the server per currency. Projects List/Archived have server-side pagination; other generic records lists still request up to 250 entries at once. New Payment Link receipts appear in Transactions but are not automatically included in invoice-only revenue reports.
5. Studio Manager records are not automatically imported from existing Client Gallery or Store orders.
6. Live end-to-end verification with a deployed MongoDB, configured SMTP and authenticated user remains necessary. Successful build and unit tests do not prove production behavior.
7. UI is tailored to the reference layouts and brand; exact pixel matching with the third-party reference product and all proprietary features is not guaranteed.
8. Calendar Sync is a read-only secret-link subscription, not two-way Google/Apple/Outlook calendar API synchronization.
9. Session cover imagery currently uses an HTTPS image URL rather than a managed file-upload flow.
10. Automatically linked projects cover bookings made after this update. Past bookings and separate Client Gallery/Store orders are not backfilled.
11. Closed paid/cancelled invoices, completed/cancelled documents and sent messages are immutable via the standard Studio API. Draft contracts are not available through public links.
12. Calendar subscriptions are not automatically refreshed by this app; clients refresh them according to their calendar application's schedule.
13. Project Details includes only directly linked documents, messages, sessions and gallery collections; older records without a project link do not appear automatically. Gallery collections can be manually linked from the project page.
14. Studio Manager session creation adds a calendar entry but does not automatically email the client. Use Send a Message for outgoing email.
15. Contract legal template paragraphs are editable *examples*, not legal advice. Have the final terms reviewed against applicable jurisdiction and the actual agreement. The owner can sign the studio side and the recipient can separately sign the client side; these are not independently identity-verified or certified digital signatures. Automated signer reminders and contract expirations remain unavailable.
16. Studio online invoice and reusable Payment Link reconciliation currently rely on the customer's return from Stripe/PayPal. If a payer closes the browser before return, a legitimate payment may remain unverified and its project might not be created until the verification is retried or manually reconciled. Add signed provider webhooks and a reconciliation job before enabling production-critical online payments. Live refund processing and webhook synchronization are not yet implemented: the Refunded tab only shows records explicitly marked refunded. Test Stripe and PayPal sandbox, new subdomains, Minio image upload, MongoDB indexes, completed/cancelled returns, duplicate payments and refunds with a staging account.

### Public owner-subdomain draft preview, Save Draft, email and invoice payments (latest)

- **Localhost link correction:** public Studio document URLs now use the backend STUDIO_PUBLIC_ROOT_DOMAIN setting independently of the development frontend. Configure STUDIO_PUBLIC_ROOT_DOMAIN=gallerista.app in backend/.env. The deployed frontend needs NEXT_PUBLIC_ROOT_DOMAIN=https://gallerista.app; local development may retain http://localhost:3000. A published share link will have the studio hostname, e.g. https://test9582.gallerista.app/studio/contract/[token]. This does not deploy or publish local drafts: the live frontend/backend must run this version and point at the same tenant/document database before such links can work outside the developer machine.

- The primary **Preview** buttons in Contract, Questionnaire, Quote, Invoice and Contact Form editors now synchronously open a new tab, save the latest draft without sending it, then navigate the tab to a real shareable URL on the studio's enabled website, for example, https://rifat39.gallerista.app/studio/invoice/{unguessable-token}. A blocked popup or failed save closes the temporary tab and displays an error. A saved draft is also shareable from the Studio Manager record list using Preview or Copy Link.
- These owner-site document links are public with **no login**: anyone with the long random token can view the draft, so it must be treated as a shareable client link and not exposed publicly on a page or in search. Draft views are read-only: no public sign, questionnaire submission, quote acceptance, form submission or checkout. The frontend routes by verified subdomain; the backend resolves enabled homepage ownership and verifies document userId and type before returning content. Public draft previews are unindexed. The previous browser-local preview remains available for the separate authenticated **Sign as Studio Owner** workflow only.
- The editors expose Save Draft and Send (or Publish for Contact Forms). Saving invoices or forms no longer automatically closes their editor. Sending a document emails the link on that same studio site, with an HTML call-to-action and a plain-text fallback. Contracts, quotes and questionnaires become **in-progress** after confirmed SMTP acceptance; invoices become **sent** (displayed as **In Progress · Sent**). A failed email attempt preserves draft status.
- Invoice emails include a **View Invoice & Pay Now** button. Customers open the subdomain's invoice page and can choose the existing Store Stripe and/or PayPal account if configured. Provider checkout returns to the same studio subdomain. The existing server-verified checkout reconciliation updates invoices to **paid** and records a transaction. Studio owners can manually record offline payments, revert a sent invoice to a draft, or cancel an unpaid invoice; completed/signed records retain their immutable protections.
- This is *verified-on-return* online payment confirmation, not a replacement for signed Stripe/PayPal webhook delivery. If a customer closes the provider page without returning, the paid status may need manual reconciliation. Test provider sandboxes, SSL/DNS, SMTP, auth cookies and MongoDB against a live staging environment before publishing.
